Team upgrade guide

A repeatable path to .NET 10

How this upgrade was done for lime-csharp, step by step. Adding a target framework is not proof of runtime readiness; the scope decisions and open gates below still apply.

Step by step

Nine upgrade steps

9 steps · commands · completion checklist

1. Inventory the repository

List the solution members and their current targets. Separate published libraries from tools, samples, and tests, and note projects outside the solution.

dotnet sln src/Lime.sln list
dotnet --list-sdks
grep -rn "<TargetFramework" src --include=*.csproj

src/Lime.sln has 19 projects, 6 of them published as NuGet packages. Lime.Client.* projects and Lime.Client.sln are outside the scope.

2. Choose the target framework policy

Libraries add net10.0 next to their existing targets so current consumers keep the same assets. Tools, samples, and tests move to net10.0 only.

Dropping netstandard2.x, net462, or net6.0 is a separate compatibility decision and was not made here.

3. Align SDK and build environments

Install the .NET 10 SDK locally. The repository has no global.json. The Azure DevOps template receives dotnetVersion: 10.x, which it passes to UseDotNet@2.

curl -sSL https://dot.net/v1/dotnet-install.sh -o dotnet-install.sh
bash dotnet-install.sh --channel 10.0 --install-dir ~/.dotnet
4. Record the baseline

Before changing anything, run restore, build, tests, and the vulnerability audit on master with the same SDK. This is what separates pre-existing failures from regressions.

dotnet restore src/Lime.sln
dotnet build src/Lime.sln --configuration Release --no-restore
DOTNET_ROLL_FORWARD=Major dotnet test src/Lime.sln --configuration Release --no-build --filter "TestCategory!=Redis"
dotnet list src/Lime.sln package --vulnerable --include-transitive
5. Resolve framework and package compatibility

Condition inbox System.* packages to the legacy targets, and use the Microsoft.AspNetCore.App framework reference instead of Kestrel 2.x on net10.0.

Package pruning in the .NET 10 SDK applies to every target of a project that targets net10.0. Remove references flagged with NU1510 instead of suppressing the warning.

6. Build in increasing scope

Fix compile errors in the project that owns them. Here, only using directives changed: the Microsoft.OpenApi 2.x namespace and a Kestrel namespace removed from ASP.NET Core 10.

dotnet build src/Lime.sln --configuration Release --no-restore --no-incremental
7. Run tests and validate runtime behavior

Run the tests on net10.0 and compare them with the baseline. A real .NET 10 regression appeared here: PipeOptions rejects a resume threshold above the pause threshold, and the fix was made in EnvelopePipe.

dotnet test src/Lime.sln --configuration Release --no-build --filter "TestCategory!=Redis" --logger trx

Current evidence: 853 of 860 tests passed. The 7 failures are pre-existing or flaky on master too. The sample smoke test and Redis-backed tests are still pending.

8. Triage NuGet security findings

Compare the post-upgrade audit with the baseline. No new advisory appeared. WebUtilities 2.3.0 remains on the netstandard2.1 asset of Lime.Transport.WebSocket.

Do not read a shorter audit as remediation: pruning hides legacy findings that consumers of the older assets still resolve.

9. Document scope and release readiness

Pack every library, inspect lib folders and nuspec dependency groups, and record the evidence in docs/dotnet-10-upgrade.md. Publishing a package with net10.0 changes its distribution contract; follow the release policy.

Do not claim performance gains from the newer runtime alone. No benchmark is part of this evidence.
